# PRD：RV64 双核访存微架构学习与日志

## 0. 文档目的

本文定义原 RVA23 学习项目结项后的独立学习阶段，供学习者和后续规划/实现工作使用。本阶段不重开或修改原阶段结项状态。它基于[阶段 Spec](../../../specs/spec-rv64-load-store-deep-dive/SPEC.md)、[可行性勘察](../../../specs/spec-rv64-load-store-deep-dive/feasibility.md)及[学习计划](../../../../learning-journal/plan.md)，聚焦 Kunminghu V2 与 Heliodor 的标量访存微架构路径，并规定如何保存探索过程、技术结论和证据。

## 1. 愿景

学习者能够通过同一架构行为比较两套 RV64 CPU 的访存实现，理解数据如何经过译码、地址生成、地址转换、缓存/存储路径，并到达结果提交或精确异常状态。每项结论都能回到固定源码快照、测试材料或实际运行产物核查。

学习过程也应能按时间回顾：每篇 Markdown 日志讲清当时的问题、查证过程、发现和后续问题，再链接到稳定的知识单元。日志保留探索脉络，知识单元保留经过整理的技术解释，运行证据独立归档。

## 2. 目标学习者

### 2.1 目标任务

- 当我学习乱序 RV64 CPU 时，我需要对照两种实现追踪同类 load/store/fault，理解架构行为如何落到不同微架构阶段。
- 当我中断后继续学习时，我需要从日志看到问题如何演进，并能快速找到对应结论和证据。
- 当我复查一个结论时，我需要知道它来自规范、静态源码、测试源码还是实际运行，避免把未知误记为已验证。

### 2.2 用户旅程

- **UJ-1. 学习者从一个待解问题走到可复习的双核结论。** 学习者从日志首页选取下一主题，阅读问题和探索步骤，检查两侧固定快照与证据，随后进入链接的知识单元复习结论；若结论依赖的行为未运行观察，日志或学习单元明确标记为 `unverified` 或 `blocked`。

## 3. 术语

- **学习日志**：按时间顺序叙述问题、探索、发现和下一步的 Markdown 文章。
- **学习单元**：按主题整理、可独立复习的技术记录，遵循项目现有学习记录约定。
- **证据**：支持某个结论的规范、设计文档、源码、测试材料或实际运行产物。
- **源码快照**：由 `sources.lock` 中稳定 ID 和完整 commit SHA 标识的 Kunminghu 或 Heliodor checkout。
- **静态路径**：通过源码连线与状态逻辑推导出的实现路径，不代表实际运行观察。
- **访存 fault**：load/store 指令执行中由地址转换或访问保护路径报告的同步异常；本阶段共同案例是 load page fault。
- **证据类型**：说明材料来源的标签，如 `spec`、`source` 或 `test-inspected`。
- **验证状态**：说明该材料或行为的核查结果的标签，如 `inspected`、`run-pass`、`blocked` 或 `unverified`。
- **非规范虚拟地址**：在当前 Sv39 场景中，VA[63:39] 不等于 VA[38] 的符号扩展；本 PRD 选择 `0x0000008000000000` 作为普通 load fault 输入。
- **运行观察**：从记录了输入、命令、配置和输出的真实构建/测试/仿真中得到的结果。

## 4. 功能

### 4.1 按时间回顾学习过程

**描述：** 学习者从仓库入口进入日志索引，按阶段和日期阅读探索过程。已有历史只根据现存文档和证据回顾，不虚构原始对话或未留存的探索细节。每篇日志链接到相应学习单元和证据。

#### FR-1：维护可导航的学习日志索引

学习者可以从仓库入口打开日志首页，并找到既有学习阶段及新阶段日志。

**可验证结果：**
- 首页区分已完成历史、正在进行和计划中的主题。
- 每篇日志链接到相关学习单元、证据或阶段规划。
- 未撰写的历史回顾标为待整理，不呈现为已经发布的文章。
- 手工核对 README 日志入口和日志索引中的全部已发布链接目标存在；计划中的未建文件以纯文本标注“待写”，不伪装成有效链接。

#### FR-2：记录每次探索

学习者可以用统一结构记录问题、探索过程、发现、证据链接和下一步；字段结构沿用[学习日志计划](../../../../learning-journal/plan.md)。

**可验证结果：**
- 日志能独立说明本次学习问题和形成的发现。
- 日志链接权威学习单元，不复制大段技术结论造成双重维护。
- 每篇日志至少记录日期、问题、查阅来源/动作、发现（含证据类型和验证状态）、知识单元/证据链接及下一步；没有内容时写 `none`、`unknown` 或 `not applicable`，不留无说明空白。
- 不能从现有材料确认的历史过程明确标为事后回顾或未知。

### 4.2 对照访存微架构路径

**描述：** 使用 `sources.lock` 固定快照，按每个实现自身的术语追踪代表案例；以可验证证据为边界，不强行对齐阶段名称。

#### FR-3：追踪成功标量 `LD`

学习者可以解释一条普通标量 `LD` 从译码/发射、地址生成、转换和缓存响应，经结果写回直到退休的、由来源证据支持的路径；未观察的阶段明确标为未知。

**可验证结果：**
- Kunminghu 与 Heliodor 各有来源支持的路径说明。
- 场景 tuple 两侧一致：RV64I `LD`、自然 8 字节对齐、M-mode Bare、无异常、DCache hit、无更老重叠 store。配置或运行无法确认的前提标为假设，不写成运行观察；若固定快照无法支撑某项路径，记录阻塞/未知并说明影响。
- 既有 [`load-v1.md`](../../../../notes/units/load-v1.md) 被复核或引用；案例实际运行结果仅在确有运行证据时记录。

#### FR-4：追踪成功标量 `SD`

学习者可以解释一条普通、自然对齐、DRAM 目标的 `SD` 从地址和数据形成，经队列与提交到实际写入通路的可证实路径。

**可验证结果：**
- Kunminghu 与 Heliodor 的路径分别按其内部结构描述。
- 用例固定为自然对齐、普通 DRAM 目标的 RV64I `SD`，不与 MMIO、未对齐或原子路径混用；精确地址和配置由故事可行性检查后记录为两侧共用的场景 tuple。
- 清楚区分指令提交、缓存/缓冲写入及更低层可见性；故事确定一个由来源证据支持的写入接受终点。若不能证明更低层可见性，标记未知，不推断 DRAM 持久可见。
- 故事需在形成路径结论前，把共用场景 tuple 和写入接受终点记入故事文档与其决策日志。
- 不从测试入口存在推断测试通过。

#### FR-5：追踪共同访存 fault

学习者可以比较 S-mode、V=0、Sv39 下普通 `LD` 使用非规范虚拟地址时的 load page fault 路径。

**可验证结果：**
- 记录两侧 fault 检测、异常保留、cause 和 trap 状态路径。
- 固定场景 tuple：S-mode、V=0、`satp.MODE=Sv39`、普通 RV64I `LD`，VA=`0x0000008000000000`（非规范），`medeleg[13]=0`。地址和 cause 由现有双侧源码记录支持。
- 追踪 `mepc`/故障 PC、`mcause=13`、`mtval` 路径、M-mode trap target 及源代码可确认的相关状态更新；实现选择或源码不能确认的 `mtval` 表示明确列为未知。
- 静态路径和动态运行状态分开；当前未动态观察的行为保持 `unverified`。

### 4.3 保存知识与证据来源

**描述：** 日志、学习单元和运行证据互相链接，并使用来源快照和证据状态保持结论可复查。

#### FR-6：区分结论与证据等级

学习者可以为主张标明支持它的证据类型和状态。

**可验证结果：**
- 每个比较结论都链接到 Kunminghu 和 Heliodor 的来源证据，或明确说明一侧缺证。
- 如果一侧缺少对照证据，相关双核比较结论保持 `unverified`/`partial`，不得写成两侧相同或等价。
- 证据类型与验证状态分开记录：类型采用 `spec`、`design-doc`、`source`、`test-inspected`、`test-run`、`experiment`；状态采用 `inspected`、`run-pass`、`run-fail`、`blocked`、`unverified`、`not-applicable`。各自占独立字段；例如运行结果使用类型 `test-run` 加状态 `run-pass`/`run-fail`。
- 实际运行结论附输入、命令、配置、输出和产物路径；未执行的测试不标为通过。
- `spec` 支持架构预期，`source` 支持静态实现路径，`test-inspected` 只支持“测试源码包含该检查/输入”的结论，`test-run` 支持实际执行的那个输入与配置；任何证据都不能支持超出其范围的泛化结论。

#### FR-7：保持来源快照可追溯

学习者可以从记录识别所用源码快照，并判断快照变化是否影响跨实现结论。

**可验证结果：**
- 记录引用 `sources.lock` 中的 snapshot ID 和 SHA。
- 只有锁定 SHA 的源码证据可计入本阶段双核比较。checkout 不匹配时停止将其结论计入验收；其他版本只能作为明确标注的背景线索，需切回锁定快照重核。
- 记录每次源码分析所用 SHA，并在学习记录完成前与 `sources.lock` 核对。

## 5. 非目标

- 修改 Kunminghu 或 Heliodor 上游 RTL。
- 证明 RVA23 全量符合性、CPU 认证或正式规范符合性。
- 穷举所有访存宽度、未对齐访问、原子/向量操作、页表组合或缓存一致性行为。
- 要求所有学习结论都有动态运行；静态路径记录可以完成学习目标，但必须标示证据边界。
- 为日志搭建或部署独立博客生成器/网站；本阶段以仓库中的 Markdown 和 GitHub 可读性为目标。
- 新增隔离 trace harness；如后续要求逐阶段运行 trace，作为新的范围变更单独评估，不自动重开本阶段验收。

## 6. MVP 范围

### 6.1 包含

- 通过 Markdown 日志索引展示现存学习历程和新的访存学习阶段。
- 完成 `LD`、`SD`、共同 Sv39 load page fault 的双核学习单元或经核对后复用现有记录。
- 更新访存追踪矩阵，链接源码快照和证据。
- 区分学习过程、稳定技术解释和原始运行证据。

### 6.2 不包含

- 强制部署静态博客或增加站点依赖；现有 Markdown 入口满足个人复习与 GitHub 阅读需要。
- 自动化逐条 trace 采集；当前 success signal 接受静态源码路径。
- 超出选定案例的性能、全面测试或符合性工作。

## 7. 成功信号

- **SM-1：** `notes/units/` 中有 `LD`、`SD` 和 fault 三项学习记录，并由 `trace-matrix.md` 对照；每个实现都有从指定起点到所选终点的路径表行，每行有源码/运行引用或明确的 `unknown`/`blocked`，验证 FR-3 至 FR-7。
- **SM-2：** `README.md` 链接到 `learning-journal/index.md`；索引区分历史回顾、新阶段日志和计划项，所有已发布链接都指向现有文件，验证 FR-1 至 FR-2。
- **反向指标：** 不以日志篇数、动态运行次数或“全部通过”措辞优化；若证据不足，明确保留 `unverified`/`blocked`，不制造表面完整性。

## 8. 开放问题

1. `SD` 用例的具体地址和内存配置由对应故事依据锁定快照的 harness/测试能力确定；故事需记录共用场景 tuple、写入接受终点和无法证实的后续可见性。
2. 既有六阶段的历史过程文章需按保存下来的证据回顾；无法还原的细节保持空缺。

## 9. 假设索引

- **[ASSUMPTION]** 目标学习者为独立学习者，主要读者是本人和技术同伴；不需要多角色审批或上线运营功能。
- **[ASSUMPTION]** 中文 Markdown、Git 仓库中的索引和链接足以满足第一版日志阅读；不需要单独部署网站。
- **[ASSUMPTION]** 当前来源静态检查足以支撑 learning-stage 完成；检查现有测试源码属于证据勘察，运行现有测试仅作为可选补充，测试运行结果不是完成门槛。
- **[ASSUMPTION]** 案例采用可行性勘察推荐的 `LD`、普通对齐 DRAM `SD` 和 Sv39 非规范 `LD` fault；故事仍需确定 `SD` 具体用例边界。

以上均为本阶段的工作假设，故事可以补充具体案例条件，但不能静默扩大范围或降低证据边界；若需改变目标，须先作为范围变更记录并修订本 PRD。

# Epic 3 Context: 解释内存与特权行为

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

学习者能够从 RISC-V 架构行为出发，沿 Kunminghu V2 与 Heliodor 的实现路径解释普通访存、原子操作以及异常或地址转换事件，并用可追溯证据比较两边设计、说明验证边界。这一阶段把前序微架构学习扩展到内存子系统和特权状态，形成可独立复习的记录；它不要求实现新 CPU 或对未检查的行为作验证声明。

## Stories

- Story 3.1: 追踪普通访存路径
- Story 3.2: 对照原子内存操作
- Story 3.3: 追踪异常或地址转换路径

## Requirements & Constraints

- 每个学习单元从有明确范围的架构行为开始，注明适用规范和排除的子案例；参数、异常、特权模式等未覆盖情形要明确列出。
- 对普通访存，追踪所选 load 或 store 的地址生成、LSU 请求、缓存或下游交互，以及响应或写入结果。对原子操作，解释所选 AMO 或 LR/SC 类别相对普通访存的架构保证，并追踪请求、原子性维护和结果/状态返回。对异常或地址转换，记录触发条件、相关特权模式、架构结果，以及事件检测、相关状态更新和后续控制流或转换结果。
- 在两种实现中沿关键数据、控制和状态变化追踪至结果；仅列模块名或代码片段不足以支持理解。每项比较结论须链接到 Kunminghu 与 Heliodor 两侧证据。结论应由源码、设计文档或验证材料支撑；无法确认的部分标为未验证。
- 使用项目锁定的来源快照和稳定 ID；每份记录引用仓库、分支及完整 commit 对应的快照，并引用适用规范版本。记录使用中文说明，ISA 名称、扩展名、符号和源码路径保留上游写法。
- 证据类型区分规范、设计文档、源码、已检查测试、实际运行测试和实验；状态区分 `inspected`、`run-pass`、`run-fail`、`unverified`、`not-applicable`。检查测试不代表已运行；只有保留了观察结果的运行才能标为通过。
- 每份单元记录保存自检问题与答案、中文总结、引用和未解问题；使用不可变 `<unit_id>-vN.md` 文件名，并在索引中指向当前版本。阶段完成须有带证据的解释、源码定位或测试/仿真检查。
- 不修改或复制上游源码。确有需要的学习者实验放在 `experiments/<unit>/`，记录来源快照、输入、步骤和观察结果。

## Technical Decisions

- 本项目采用证据驱动的双实现对照：从规范行为开始，分别记录 Kunminghu 与 Heliodor 路径，再形成有两侧证据 ID 的比较结论。
- 沿用统一学习记录结构：单元自检、架构行为及子案例、Kunminghu 路径、Heliodor 路径、比较结论、证据表、学习者总结、未解问题。记录位置、行号或固定 commit 链接，避免仅依赖会移动的分支位置。
- 将“源码检查”“检查过的测试”和“实际运行”作为不同证据状态报告。若工具链或配置使运行无法进行，保留阻塞原因并以可获得的源码/规范证据说明边界，不推断测试通过。
- 项目依据官方规范描述架构要求；上游自述、局部 RTL 或单个测试均不等同于完整符合性或认证结论。Epic 3 的局部学习记录也不代替 Epic 4 的 RVA23 必选要求映射。

## Cross-Story Dependencies

- Epic 3 是候选阶段，只有 Story 1.3 的 ADD 复盘明确记录 `ready`、授权 Epic 3 并确认范围与节奏后才可启动；`adjust` 或 `defer` 均不能作为启动依据。
- 阶段 3 依赖路线中此前阶段的学习记录与检查通过。Epic 2 对应乱序阶段；如复盘批准 Epic 3 而未批准 Epic 2，仍须遵从已确认的范围和学习路线先修条件，不假定候选史诗自动获批。
- 三个故事共用锁定的来源快照、证据规则和记录模板；各自的结论及自检应保留在独立版本化单元中。

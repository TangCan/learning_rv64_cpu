# ADD 试点复盘

日期：2026-10-12

## 试点结果

`notes/units/add-v1.md` 按 Story 1.2 模板记录了 RV64I `ADD` 的规范行为、边界、两边译码至整数写回路径、比较结论、自检答案、证据状态和未解问题。两条比较结论均关联 Kunminghu 与 Heliodor 的证据 ID。所有上游源代码只读；本试点没有运行 CPU 构建、仿真或测试。

## 模板复用点

- Frontmatter 的单元范围、排除项、规范版本及双快照 SHA 适合固定每份记录的比较边界。
- 按顺序使用架构子案例、两边路径、双边证据的比较表和统一证据表，能把 ISA 行为连到 decode、execute、writeback。
- 自检问题/答案与总结、未解问题能保留可复习内容；对测试使用 `inspected`/`unverified`，没有将入口或向量误写成通过。
- 索引通过不可变版本文件指向当前单元，满足后续迭代时保留历史记录的需要。

## 实际缺口与建议

1. 模板已有完整证据字段，但对证据表中“不运行测试”的具体状态表达容易含糊。建议后续单元将测试源码检查记为 `test-inspected / inspected`，测试执行项单独列为 `test-run / unverified`，命令明确写 `not-run` 并说明阻塞。本试点已按此方式填写 E8、E9、E14。
2. 模板未专门提醒学习者验证测试断言覆盖的具体案例。建议每次检查 testbench 时记录输入向量、断言发生的周期/分支、计数器状态和 `done` 条件，不能仅凭向量或一次总体断言推断覆盖。Heliodor 的 testbench 运行 29 次时钟迭代后断言一次 `pass`，但未等待 `done` 或检查 `tc`；静态源码无法确认该断言对应的案例，因此 ADD 和 DIV 均不能据此视为已断言。本试点通过 E14 记录了此缺口。
3. 模板不强制把规范允许忽略的算术溢出与实现位宽对应起来。建议在算术类单元子案例中明确结果位宽、溢出行为、`W` 变体，并将这些作为待检查边界；本记录已在架构表列出。
4. 本单元的源码路径足以说明数据流，但未追踪 `rd=x0`、异常/冲刷和多种边界输入。之后按单元目标缩小范围并列为未覆盖项，不把单条指令记录扩写成完整符合性结论。
